# gamba — Architecture

> High-level architecture of the gamba v1 monorepo: stack, layout, module
> boundaries, data model, the WebSocket protocol, and the round engine.
>
> Source of truth for _what_ the product does: [`SPEC.md`](./SPEC.md). Where
> this document and the spec disagree, the spec wins — intentional departures
> from the legacy code bases are listed in §14.
>
> The final section (§16 "Build order") is a temporary construction checklist
> and should be removed once v1 ships.

## 1. Guiding principles

- **One feature, done well**: a shared, real-time crash game. No speculative
  abstraction.
- **Server-authoritative outcomes, client-side animation.** The curve is
  deterministic from the round start time, so clients animate locally; the
  server owns every coin-moving decision (bet accepted, cashout multiplier,
  crash).
- **Single source of truth for shared logic.** The crash formulas, the
  provably-fair derivation, and the WS message schemas live in one package
  imported by both apps, so client animation and server authority can never
  drift apart.
- **Bun only, everywhere**, enforced mechanically.
- Code comments and docs are written in English.

**Server — split by concern.** Three top-level buckets keep transports and
infrastructure apart: `db/` is pure infrastructure; `modules/` holds the REST
API (one Hono router per resource, including `history` — the recent-rounds and
personal-bets read models are HTTP, not WS); `game/` is the single real-time
feature, where `engine.ts` is transport-agnostic domain logic and `ws.ts` is the
only place that knows about WebSockets. (If a second transport ever appears, the
engine can be split into a `realtime/` layer without touching the domain — not
needed for v1.)

**Web — feature-based (bulletproof-react).** `app/` wires providers and the
router; `pages/` are thin route shells; each `features/*` slice owns its `api/`,
`components/`, and `hooks/` and exposes a small public surface via `index.ts`;
truly generic UI lives in `components/`. This scales by adding a feature folder
rather than growing a flat tree. Feature-Sliced Design was considered but is
oversized for a two-screen app. Component names are illustrative and their
styling is the `/design` role's call — this document only fixes the
data/behaviour boundaries.

## 4. `packages/shared` (the anti-drift core)

Everything both sides must agree on lives here. The crash math is ported from
the legacy `crash-games.helper.ts`, which is already correct.

- **`crash.ts`**
  - `K = 0.0578`, `HOUSE_EDGE_PERCENT = 5`.
  - `multiplierFromMs(elapsedMs): number` → integer, ×100 (e.g. `150` = 1.50×).
    `floor(exp(K · elapsedMs/1000) · 100)`.
  - `crashFromSeed(seed): number` → integer ×100, min `100`, 5% edge (the exact
    legacy `getCrashTickFromSeed` math: 52-bit hash slice → `(100e − h)/(e − h)`
    → apply edge → `max(100, …)`).
  - `msFromMultiplier(mult): number` → inverse, used server-side to schedule the
    crash and to compute a cashout multiplier from a timestamp.
- **`fair.ts`**: `sha256Hex(input)` for commit and client-side verification.
- **`protocol.ts`**: one Zod schema per inbound and outbound message (payload
  shapes in §6), plus the discriminated-union type of all messages. Both the
  server (validate inbound) and the web client (type outbound + parse inbound)
  import these.
- **`constants.ts`**: `BETTING_WINDOW_MS = 20_000`, `FINISHED_PAUSE_MS = 5_000`,
  `START_COINS = 1000`, `FAUCET_THRESHOLD = 100`, `FAUCET_GRANT = 1000`,
  `MIN_BET = 1`.

## 5. Database schema (Drizzle / PostgreSQL)

Four tables. UUID primary keys, `created_at` defaults. Enums as Postgres enums
(preferred) or `text` + Zod guard.

- **`users`**: `id (uuid pk)`, `name (text unique)`, `email (text unique)`,
  `password_hash (text)`, `coins (integer, >= 0, default 1000)`,
  `created_at`.
- **`sessions`**: `id (uuid pk)`, `user_id (fk users)`, `expires_at`,
  `created_at`. The cookie carries the signed session id.
- **`rounds`**: `id (uuid pk)`, `seed (text)`, `seed_hash (text)`,
  `crash_multiplier (integer, ×100, nullable until finished, stays null if
aborted)`, `state (enum: pending|in_progress|finished|aborted)`, `created_at`,
  `started_at (nullable)`, `ended_at (nullable, set on finish or abort)`.
- **`bets`**: `id (uuid pk)`, `user_id (fk)`, `round_id (fk)`,
  `amount (integer)`, `status (enum: pending|cashed_out|crashed|refunded)`,
  `cashed_out_at (integer ×100, nullable)`, `created_at`.
  Unique constraint on `(user_id, round_id)` → enforces "one bet per round" at
  the DB level.

**Coin integrity.** All coin movements go through a transaction with a
conditional update so concurrent messages can never double-spend or
double-credit:

- Debit at bet: `UPDATE users SET coins = coins - :amount WHERE id = :id AND
coins >= :amount` — zero rows updated ⇒ reject (`NOT_ENOUGH_COINS`). Insert
  the bet in the same tx; the unique `(user, round)` index rejects a second bet.
- Credit at cashout: flip the bet `pending → cashed_out` with a guarded update
  (`WHERE status = 'pending'`) then `coins = coins + floor(amount·mult/100)`;
  zero rows ⇒ already cashed out.
- Refund on abort: in one tx, flip the round to `aborted` (guarded
  `WHERE state IN ('pending','in_progress')`), flip its bets
  `pending → refunded` (guarded `WHERE status = 'pending'`) and credit
  `coins = coins + amount` for exactly the rows flipped — a refund can never be
  applied twice. Cashed-out bets are left untouched.

## 6. WebSocket protocol

Native Bun WS, **one connection** at `/ws` (Socket.IO and its two namespaces
are dropped). Broadcasts use Bun's pub/sub: every socket subscribes to the
`"game"` topic and the server calls `server.publish("game", …)`. Per-client
replies are sent on the socket directly.

**Connection & identity.** The WS upgrade runs behind the Vite dev proxy, so it
is same-origin and the httpOnly session cookie is sent automatically. On upgrade
the server resolves the session → attaches `userId` (or `null` for a spectator)
to the socket's context data. No token in the URL (legacy did `?token=`;
dropped).

Every message is a JSON envelope `{ type, payload }`, validated against the
`packages/shared` Zod schema for that `type`.

**Client → server**

| type      | when          | payload           | notes                        |
| --------- | ------------- | ----------------- | ---------------------------- |
| `bet`     | pending phase | `{ amount: int }` | requires auth; one per round |
| `cashout` | in-progress   | `{}`              | requires a pending bet       |

(No explicit "connected" handshake message — identity is resolved at upgrade,
and the server pushes `round:state` immediately on connect.)

**Server → client**

| type            | trigger                       | payload                                                                       |
| --------------- | ----------------------------- | ----------------------------------------------------------------------------- |
| `round:state`   | on connect + on phase change  | full snapshot: phase, roundId, seedHash, startTime?, bets[], crashMultiplier? |
| `round:pending` | new betting window opens      | `{ roundId, seedHash, bettingEndsAt }`                                        |
| `round:start`   | betting closes, curve begins  | `{ startTime }` (epoch ms; clients animate from here)                         |
| `round:crash`   | round ends                    | `{ crashMultiplier, seed }` (seed revealed here)                              |
| `round:aborted` | engine failure mid-round      | `{ roundId }` (pending bets refunded; clients refetch balance + history)      |
| `bet:new`       | any player bet accepted       | `{ roundId, userName, amount }`                                               |
| `bet:cashout`   | any player cashout            | `{ roundId, userName, multiplier }`                                           |
| `presence`      | connect/disconnect/bet change | `{ connected: int, inRound: int }`                                            |
| `error`         | rejected client action        | `{ code, message }` (codes ported from legacy `WsError`)                      |

**Sync for mid-round joiners.** `round:state` carries the current phase plus
`startTime`, so a late client's local animation lines up with everyone else's.

REST (over HTTP, not WS) handles request/response concerns:

- `POST /api/auth/register`, `POST /api/auth/login` → set session cookie.
- `POST /api/auth/logout` → clear session.
- `GET /api/auth/me` → current user (balance included) or 401.
- `POST /api/users/faucet` → claim (guarded by threshold).
- `GET /api/history/rounds` → 10 most recent **finished** crashes (aborted
  rounds excluded).
- `GET /api/history/bets` → 25 most recent bets of the logged-in user
  (refunded bets included).

## 7. Round lifecycle engine (server-authoritative)

A single in-memory singleton (`game/engine.ts`) drives the round state machine.
It holds `currentRound` and drives transitions with timers, persisting each
transition.

```
CREATE (pending)                         START (in_progress)                 END (finished)
──────────────────                       ───────────────────                 ─────────────────
new seed + hash                          persist started_at                  persist crash mult
persist round (state=pending)            bets already debited (see §14)      pending bets -> crashed
publish round:pending {hash, endsAt}     schedule END at msFromMultiplier    publish round:crash {mult, seed}
schedule START in BETTING_WINDOW_MS      publish round:start {startTime}      schedule CREATE in FINISHED_PAUSE_MS
```

- **Crash timing** is derived from the seed: `crash = crashFromSeed(seed)`,
  `durationMs = msFromMultiplier(crash)`. The END timer fires at
  `startTime + durationMs`. This value is authoritative; the client animation is
  display-only and never decides the outcome.
- **`startTime`** is the exact epoch ms the curve begins (set when START fires),
  broadcast to all clients. `multiplierFromMs(now − startTime)` is the single
  formula both the client (display) and the server (cashout value) use.
- **Cashout authority**: on a `cashout` message, the server checks the round is
  `in_progress` and `now < startTime + durationMs`; if so the awarded multiplier
  is `multiplierFromMs(now − startTime)` (never above the crash point). If the
  window has passed, reject — the round has effectively crashed.
- **Presence**: `connected` = open sockets; `inRound` = bets in `currentRound`.
  Recomputed and published on connect, disconnect, and each accepted bet.
- **Disconnect during a round**: the bet stays; since cashout is manual, a
  disconnected player's pending bet resolves as `crashed` at END.

**Aborted rounds.** A single `abortRound(roundId)` (refund tx in §5) is used in
two places:

- **Boot recovery**: before creating its first round, the engine aborts every
  round still `pending` or `in_progress` in the DB (left over by a restart,
  crash or kill).
- **Engine failure**: if a transition (CREATE/START/END) throws, the engine
  clears its timers, aborts the current round, publishes `round:aborted`, then
  schedules a fresh CREATE. If the abort itself fails (e.g. DB down), the round
  stays unresolved in the DB and boot recovery picks it up later.

Graceful shutdown (SIGINT/SIGTERM) is deliberately not handled: boot recovery
already covers it.

## 8. Frontend data flow

- **Auth**: `/auth` posts to REST; on success the cookie is set and TanStack
  Query's `me` query is invalidated → app shows `/game`. `GET /me` on load
  restores the session (stay-logged-in across reloads). A React Router guard
  redirects unauthenticated users appropriately (spectators may still watch the
  game read-only per SPEC §4 — betting controls are gated on auth).
- **Game real-time**: `WsProvider` opens the single WebSocket, parses each
  inbound message with the shared Zod schema, and updates a small store (round
  phase, current bets, presence, recent results). `useMultiplier` runs a
  `requestAnimationFrame` loop computing `multiplierFromMs(now − startTime)` from
  `packages/shared` — the same code path as the legacy `InProgress.tsx`, minus
  the hard-coded constants.
- **History**: `ResultsStrip` and `PersonalHistory` load via TanStack Query REST
  calls; `ResultsStrip` is also refreshed when a `round:crash` arrives. Aborted
  rounds never appear in the strip; refunded bets appear in `PersonalHistory`
  with a disabled/cancelled style. On `round:aborted`, `me` and the personal
  history are refetched.
- **Routes**: `/game` is public (spectators watch read-only), `/` redirects to
  it; `/auth` redirects to `/game` when already logged in.
- **Errors**: `error` WS messages and REST 4xx map to the shared error codes for
  clear, localized messages.

## 9. Auth & session

- Register: validate email + name uniqueness (DB unique + friendly error),
  `password_hash = await Bun.password.hash(pw)` (argon2id), create user with
  `coins = 1000`, open a session, set cookie.
- Login: `Bun.password.verify`; on success open a session + cookie.
- Session cookie: `httpOnly`, `sameSite=lax`, `secure` in prod, signed; value =
  session id looked up in `sessions`. Logout deletes the session row + clears
  the cookie.
- The WS upgrade reuses the same session lookup, so HTTP and WS share one
  identity mechanism.

## 10. Economy & faucet

- Start balance 1000 (constant in `shared`).
- Faucet (`POST /api/users/faucet`): allowed **only** when `coins < 100`; grants
  a flat `+1000`; **no cooldown**. Implemented as a guarded update
  (`WHERE coins < 100`) so a double-click can't stack grants.
- Bet accounting per SPEC §5.2, enforced by the transactional updates in §5.

## 11. Provably-fair

The crash point is fully determined by the round's server seed. See
[`PROVABLY-FAIR.md`](./PROVABLY-FAIR.md) for the verification guide.

- **Commit**: `round:pending` broadcasts `sha256(seed)` (seed stays secret).
- **Play**: crash point = `crashFromSeed(seed)`.
- **Reveal**: `round:crash` broadcasts the plain `seed`.
- **Verify**: hash the revealed seed, match the earlier commit, recompute the
  crash point. v1 is server-seed only (documented simplification).

## 12. Bun-only enforcement

- Root `package.json`: `"packageManager": "bun@<version>"` and a `preinstall`
  guard that checks `npm_config_user_agent`/`npm_execpath` and exits non-zero
  for npm/yarn/pnpm.
- Commit `.npmrc`/`.yarnrc` guards if needed; document the rule in README.
- `bunfig.toml` for workspace + install config.

## 13. CI (GitHub Actions)

`.github/workflows/ci.yml`, on push + PR:

1. `oven-sh/setup-bun`.
2. `bun install --frozen-lockfile`.
3. Lint (root script fanning out to both apps + shared).
4. Type check (`tsc --noEmit` per package/app).
5. Build (`apps/web` vite build; `apps/server` type-check/build).

DB is not required for these steps (no integration tests in v1 scope). If a
smoke test later needs Postgres, add a `services: postgres` block.

## 14. Design decisions (departures from the legacy code)

| Topic           | Legacy behaviour                              | v1                                                   |
| --------------- | --------------------------------------------- | ---------------------------------------------------- |
| Auth            | Magic-link (email only, nodemailer, tokens)   | Email + password, hashed, cookie session             |
| Coin debit      | Debited at round **start** (`register…start`) | Debited at **bet placement** (SPEC §5.2)             |
| Start balance   | 200                                           | **1000**                                             |
| Faucet          | none                                          | claim `<100 → +1000`, no cooldown                    |
| Transport       | Socket.IO, 2 namespaces                       | native Bun WS, one connection, pub/sub topic         |
| DB / ORM        | MySQL + MikroORM (decorators)                 | PostgreSQL + Drizzle                                 |
| Frontend        | Next.js (SSR, app router)                     | React SPA (Vite, React Router)                       |
| Curve constants | duplicated in `InProgress.tsx`                | single `packages/shared/crash.ts`                    |
| Seed exposure   | computed but not broadcast                    | hash on pending, seed on crash                       |
| Cashout timing  | `getCrashTickFromTime(now − (created+20000))` | `multiplierFromMs(now − startTime)`, bounded < crash |

The cashout-timing change matters: legacy assumed `start = created_at + 20000ms`
(implicit). v1 broadcasts an explicit `startTime` set when the curve actually
begins, removing the hidden coupling to the betting window length.

## 15. Known limitations & operational notes

- **Timer drift / crash precision.** `setTimeout` is not exact. The awarded
  cashout multiplier is computed from timestamps + the seed-derived duration,
  never from a tick counter, so display drift never affects payouts. The END
  guard (`now < startTime + durationMs`) uses the same duration the client
  cannot exceed.
- **Cookies over WS in dev.** Cross-origin (`:5173` vs `:3000`) would drop the
  session cookie on the WS upgrade. The **Vite dev proxy** for `/api` and `/ws`
  keeps everything same-origin — without it, auth-over-WS appears broken.
- **Single-process game state.** The round engine is an in-memory singleton; v1
  runs one server instance (no horizontal scaling — out of scope). A restart
  mid-round abandons the current round; it is marked `aborted` and its pending
  stakes are refunded at the next boot (§7).
- **Concurrency correctness.** Double-bet / double-cashout / double-faucet all
  rely on guarded conditional updates + the `(user, round)` unique index rather
  than app-level checks alone. This is the one area to test deliberately.
- **Floor semantics.** Winnings floored to whole coins (`floor(amount·mult)`);
  multipliers are integers ×100 end-to-end to avoid float drift, matching the
  legacy convention.
